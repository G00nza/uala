❯ a que te referis con fan-out?                                                 

⏺ Cuando un usuario publica un tweet, el sistema lo "dispersa" inmediatamente a
  los timelines en Redis de todos sus seguidores.

  Ejemplo concreto: El usuario A tiene 3 seguidores (B, C, D). Cuando A postea
  un tweet:
  - Se guarda el tweet en PostgreSQL
  - Se escribe ese tweet en la lista de timeline de B en Redis
  - Se escribe ese tweet en la lista de timeline de C en Redis
  - Se escribe ese tweet en la lista de timeline de D en Redis

  Cuando B pide su timeline → Redis responde en O(1), sin tocar la base de
  datos.

  La alternativa sería fan-out on read: cuando B pide su timeline, se hace un
  JOIN en PostgreSQL de todos los usuarios que B sigue y sus tweets. Más simple,
   pero lento a escala.

  Las consignas piden explícitamente "optimizada para lecturas", por eso elijo
  fan-out on write.

⏺ ---
  Sección 3 — Arquitectura interna (Clean Architecture)

  uala/
  ├── cmd/
  │   └── api/          # main.go, wiring de dependencias
  ├── internal/
  │   ├── domain/       # entidades y errores de dominio
  │   ├── usecase/      # lógica de negocio
  │   ├── handler/      # HTTP handlers (chi o net/http)
  │   ├── repository/   # implementaciones de persistencia (postgres, redis)
  │   └── infra/        # clientes externos (rabbitmq, prometheus)
  ├── migrations/       # archivos SQL
  ├── docker-compose.yml
  └── Makefile

  Flujo por capa:
  Handler → UseCase → Repository (PostgreSQL / Redis)
                    → Infra (RabbitMQ publisher)

  El domain define interfaces (puertos). repository e infra son las
  implementaciones (adaptadores). El usecase no importa nada de infra
  directamente, solo habla con interfaces.

  Esto permite, por ejemplo, swappear PostgreSQL por cualquier otra DB sin tocar
   la lógica de negocio.

❯ no estoy entendiendo la parte de redis                                        

⏺ Un Sorted Set de Redis es una lista donde cada elemento tiene un score
  numérico que define el orden.

  En este caso, cada usuario tiene su propia lista de tweets en Redis:

  timeline:user-B  →  [ tweet-id-3 (score: 1714000300),
                         tweet-id-1 (score: 1714000100),
                         tweet-id-2 (score: 1714000050) ]

  El score es el timestamp del tweet. Redis los mantiene ordenados
  automáticamente, así ZREVRANGE te devuelve siempre los más recientes primero.

  ¿Cómo se construye?

  Cuando el usuario A (al que sigue B) publica un tweet:
  1. Se guarda el tweet en PostgreSQL
  2. Se buscan todos los seguidores de A (B, C, D...)
  3. Se agrega el tweet_id con su timestamp a timeline:B, timeline:C, timeline:D

  Cuando B pide su timeline:
  - Redis devuelve los últimos N tweet_ids de timeline:B
  - Se busca el contenido de esos tweets (en PostgreSQL, o también cacheado en
  Redis)

⏺ ---
  Sección 5 — Mensajería (Iter 3)

  Cuando POST /tweets recibe un tweet, en lugar de hacer el fanout a Redis de
  forma sincrónica (bloqueando la respuesta HTTP), publica un evento a RabbitMQ
  y responde inmediatamente al cliente.

  Flujo:

  POST /tweets
      → guarda tweet en PostgreSQL
      → publica evento { tweet_id, user_id, content, created_at } a RabbitMQ
      → responde 201 al cliente

  Consumer (goroutine independiente)
      → recibe evento de la queue
      → busca seguidores del user_id en PostgreSQL
      → hace fanout: agrega tweet al Sorted Set de cada seguidor en Redis

  Ventaja clave: el cliente no espera el fanout. Si un usuario tiene 100.000
  seguidores, el HTTP response es igual de rápido que si tuviera 1.

  Trade-off a documentar: el timeline tiene consistencia eventual — un seguidor
  puede ver el tweet con algunos milisegundos/segundos de delay después de
  publicado.

  POST /follow
      → guarda follow en PostgreSQL

      → responde 201 al cliente

  Consumer

      → busca últimos N tweets de followee_id en PostgreSQL
