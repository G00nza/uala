❯ los handlers tienen una interfaz del use case que usan, esto es algun patron  
  de go?                                                                        

⏺ Skill(golang:interfaces)
  ⎿  Successfully loaded skill

⏺ Sí, es exactamente el principio "accept interfaces, return concrete structs"
  de Go.

  El handler define la interfaz del use case que necesita (en su propio paquete,
   no en el del use case):

  // handler/user.go — la interfaz vive ACÁ, no en usecase/
  type userUseCase interface {
      CreateUser(ctx context.Context, input CreateUserInput) (*User, error)
  }

  type UserHandler struct {
      uc userUseCase
  }

  El use case concreto simplemente implementa esa interfaz implícitamente (duck
  typing de Go):

  // usecase/user.go
  type UserUseCase struct { repo UserRepo }

  func (u *UserUseCase) CreateUser(...) (*User, error) { ... }
  // ↑ cumple la interfaz del handler sin saberlo

  Por qué hacerlo así:

  - El handler declara exactamente los métodos que necesita — si el use case
  tiene 10 métodos pero el handler solo usa 2, la interfaz tiene 2.
  - Testear el handler es trivial: solo implementás los 2 métodos del mock, no
  toda la struct.
  - El use case no depende del handler para nada — la dependencia va en una sola
   dirección.

  Es la aplicación del Interface Segregation Principle combinado con la
  convención Go de definir interfaces en el consumidor, no en el proveedor.

❯ no entiendo el racional de abstraer un use case con una interfaz, por         
  definicion, un use case solo tiene que tener un punto de entrada publico y en 
   la estructura DDD el handler se ubica en una capa exterior a los casos de    
  uso                                                                           

⏺ Tenés razón, hay una tensión real ahí.

  En DDD estricto el flujo de dependencias es handler → use case, y el use case
  es la capa más "pura". Crear una interfaz del use case en el handler
  contradice la dirección natural de esa dependencia y viola el principio de que
   las abstracciones viven en la capa más interna, no en la exterior.

  Lo que tiene sentido en DDD:

  La abstracción debería vivir en la capa de aplicación como un input port, no
  en el handler:

  // application/port/in/create_user.go
  type CreateUserUseCase interface {
      Execute(ctx context.Context, input CreateUserInput) (*User, error)
  }

  El handler depende del puerto, no del use case concreto. La diferencia es que
  la abstracción es responsabilidad de la capa de aplicación, no del handler.

  Cuándo la interfaz en el handler tiene sentido:

  Solo para testing de unidad del handler en aislamiento. Si el test del handler
   no le importa la lógica del use case, definir una interfaz mínima en el
  paquete del handler es pragmático en Go.

  El argumento en contra que planteás:

  Si los tests del handler son de integración (levantan el use case real con
  repos mockeados), la interfaz en el handler es ruido puro — cumple la Go
  convention pero no aporta nada arquitecturalmente.

  La conclusión honesta: el patrón de "interfaz del use case en el handler" es
  una convención Go pragmática para unit testing, no un patrón DDD. En
  arquitectura estricta, el input port pertenece a la capa de aplicación.

  decisions.md con esta decision y despues quiero que cambies todos los         
  handlers

❯ dejaste las interfaces en port, por que?                                      

⏺ Buena pregunta — es una decisión cuestionable. Puse todas las interfaces en
  port.go por simetría con el nombre "ports", pero en Go lo idiomático es
  co-ubicar la interfaz con su implementación.

  UserCreator vive junto a UserUseCase en user.go, TweetCreator junto a
  TweetUseCase en tweet.go, etc. Un lector que abre user.go ve el contrato y la
  implementación en el mismo lugar, sin saltar a otro archivo.

  port.go solo tiene sentido si querés un punto único de entrada para documentar
   todos los puertos — útil cuando hay muchos casos de uso o cuando el proyecto
  es lo suficientemente grande como para que ese índice tenga valor. En este
  codebase es overhead sin beneficio real.

  ¿Lo muevo a cada archivo respectivo y elimino port.go?
