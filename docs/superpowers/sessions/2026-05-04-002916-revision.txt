  ---
  Análisis de Gaps — Desafío Ualá

  Lo que está bien hecho

  El proyecto está sólido en muchos aspectos: clean architecture correcta con
  dependencias solo hacia adentro, Redis sorted set para timeline optimizado
  para lectura, RabbitMQ para fanout asíncrono, manejo correcto de Unicode en
  tweets (utf8.RuneCountInString), tests unitarios y de integración separados,
  OpenAPI spec, ADRs, métricas Prometheus/Grafana, y Docker Compose completo.

  ---
  Gaps Detectados

  1. Producción Go — Graceful Shutdown (Gap crítico)

  main.go usa http.ListenAndServe sin manejo de señales SIGTERM/SIGINT. Los
  goroutines consumidores de RabbitMQ reciben un context.Background() que nunca
  cancela. En producción, un deploy/restart mataría conexiones y mensajes en
  vuelo sin vaciado del buffer.

  Lo esperado: signal.NotifyContext, shutdown del servidor con timeout, y
  cancelación del contexto propagada a consumidores.

  ---
  2. Bug en tests — Constructor con aridad incorrecta (Gap de atención al 
  detalle)

  En handler/integration_test.go (o setup_test.go) hay una llamada:
  redisrepo.NewTimelineRepository(testRDB, pgTimeline)  // 2 args
  Pero el constructor real requiere 3 argumentos (incluye limit int). Los tests
  de integración no compilan tal como están.

  ---
  3. Publish errors silenciosos sin logging (Gap de observabilidad)

  _ = uc.publisher.PublishTweetCreated(ctx, event)
  La pérdida del evento ni siquiera se loggea. Hay métricas de
  rabbitmq_messages_failed_total en el consumer pero no en el publisher. Un
  fallo de conexión a RabbitMQ al publicar es invisible salvo por síntomas
  downstream.

  ---
  4. No hay lógica de reconexión en el consumer (Gap de resiliencia)

  Si la conexión AMQP cae, el consumidor muere sin reintentar. No hay Dead
  Letter Queue (DLQ) configurada, y el Nack(..., requeue=true) puede crear un
  loop infinito si el mensaje siempre falla.

  Lo esperado para producción: DLQ, backoff exponencial en reconexión, y un
  límite de reintentos por mensaje.

  ---
  5. Fanout no escala a millones de seguidores (Gap de diseño para escala)

  El consumer de tweet.created hace un GetFollowers y luego escribe a Redis
  secuencialmente para cada seguidor. Para un usuario con 1M seguidores, esto
  bloquea el único goroutine consumidor durante minutos.

  El enunciado pide explícitamente escalar a millones de usuarios. Lo esperado:
  fanout concurrente con errgroup/semáforo, o un modelo híbrido push/pull
  (fanout solo para usuarios activos, pull para celebrities).

  ---
  6. Sin paginación en timeline (Gap funcional)

  GET /timeline devuelve hasta 500 tweets en una sola respuesta. No hay
  cursor-based pagination ni limit/offset en la API. El OpenAPI spec menciona
  paginación como "backlog" pero no está implementada.

  ---
  7. Migraciones inline en startup (Gap de madurez en DB management)

  Migrate() ejecuta CREATE TABLE IF NOT EXISTS directamente en el arranque del
  servidor. No usa herramientas estándar como golang-migrate, goose o atlas.

  El riesgo: cambios de schema en producción sin versionado ni rollback
  capability.

  ---
  8. No hay validación de existencia del usuario en el contexto (Gap de 
  seguridad básica)

  parseUserID lee el header X-User-ID como UUID pero no verifica que el usuario
  exista en ningún endpoint autenticado (solo CreateTweet y Follow lo verifican
  via repositorio). Un UUID válido pero inexistente puede comportarse de forma
  inconsistente.

  ---
  9. Use cases sin interfaz propia (Gap de diseño — debatible)

  El ADR-001 justifica esto con "private interfaces en handlers como testing
  seam", pero esto impide mockear use cases entre sí si alguna vez un use case
  necesita llamar a otro, y complica la transición a arquitecturas como gRPC
  donde las interfaces de servicio son el contrato. Es una decisión válida
  documentada, pero muestra desconocimiento del trade-off completo.
