⏺ El problema está claro en líneas 118-122: el loop de fanout es secuencial. Acá
   está la solución:

  ---
  El problema

  // Secuencial — 1M seguidores = 1M AppendTweet en serie
  for _, followerID := range followers {
      if err := c.fanout.AppendTweet(ctx, followerID, item); err != nil { ... }
  }

  Con 1M seguidores, cada AppendTweet es una escritura a Redis. Secuencialmente,
   a ~1ms por operación, son ~16 minutos bloqueando el único goroutine
  consumidor.

  ---
  La solución: fanout concurrente con semáforo

  Reemplazar el loop en handleTweetCreated (línea 118):

  const fanoutConcurrency = 100

  func (c *Consumer) handleTweetCreated(ctx context.Context, d amqp.Delivery) {
      // ... unmarshal y GetFollowers igual que antes ...

      g, gctx := errgroup.WithContext(ctx)
      sem := make(chan struct{}, fanoutConcurrency)

      for _, followerID := range followers {
          fid := followerID
          sem <- struct{}{}
          g.Go(func() error {
              defer func() { <-sem }()
              if err := c.fanout.AppendTweet(gctx, fid, item); err != nil {
                  log.Printf("rabbitmq: fanout tweet to %s: %v", fid, err)
                  // no retornamos error para no cancelar todo el fanout por un 
  fallo parcial
              }
              return nil
          })
      }

      _ = g.Wait()
      // ... métricas y Ack ...
  }

  Con 100 goroutines paralelas, 1M seguidores pasan de ~16 min a ~2.5 min. Con
  1000, a ~15 segundos.

  ---
  Por qué no retornar el error individual

  En fanout, si falla escribir para 1 de 1M seguidores, no queremos hacer Nack y
   re-procesar 1M escrituras. Lo correcto es loggear el fallo parcial y hacer
  Ack igual (consistencia eventual). Si quisieras más garantías, usarías un
  retry local o DLQ por follower, no por evento.

  ---
  Modelo híbrido push/pull (para "celebrities")

  Si el sistema tiene usuarios con muchos seguidores (>100K), el mejor approach
  es:

  - Push (fanout activo): solo para seguidores que estuvieron activos
  recientemente
  - Pull (al leer timeline): si el autor tiene >N seguidores, se consulta su
  feed directamente al leer

  Esto elimina el fanout de celebrities por completo. Twitter/X usa exactamente
  este modelo. Es más complejo de implementar pero escala a miles de millones.

  ---
  El cambio mínimo para resolver el gap es el fanout con errgroup + semáforo.
  ¿Querés que lo implemente directamente en el código?

  // si la key NO existe en Redis → cae a Postgres

  indefinidamente.

  1. TTL en las keys de Redis — el cache expira, el siguiente read cae a
  Postgres que tiene el tweet. Simple, pero aumenta la carga en Postgres.

  letter queue para reintentar solo los writes que fallaron. Más complejo, no
  reprocesa todo el fanout.
  3. Modelo híbrido en lectura — GetTimeline siempre mergea Redis + los últimos
  N tweets de Postgres para el usuario. Costoso pero robusto.

  La opción 1 es la más simple y directamente relacionada con el Gap #3 del
  documento (sin DLQ). ¿Querés implementar el TTL en las keys como solución

  │                       │ exchange  │                                     │
  ├───────────────────────┼───────────┼─────────────────────────────────────┤
  │                       │           │ x-message-ttl: 30000,               │
  │ fanout.wait queue     │ durable   │ x-dead-letter-exchange:             │
  │                       │           │ fanout.retry.exchange               │
  ├───────────────────────┼───────────┼─────────────────────────────────────┤
  │ fanout.dead queue     │ durable   │ — (replay manual)                   │
  └───────────────────────┴───────────┴─────────────────────────────────────┘

  Flujo:
  1. AppendTweet falla → consumer publica en fanout.retry
  2. ConsumeFanoutRetry intenta AppendTweet
  3. Si falla → Nack(requeue=false) → RabbitMQ DLX lo manda a fanout.wait → TTL
  30s → vuelve a fanout.retry
  4. El header x-death[fanout.retry].count es el contador nativo de RabbitMQ
  5. Cuando count >= 10 → consumer publica manualmente a fanout.dead, incrementa
   métrica, Ack

  Trade-offs anotados:
  - Config declarativa de exchanges/bindings/TTL en el arranque del servidor
  - Más difícil de testear sin broker real (setup complejo en integration tests)
  - Lógica distribuida: el backoff lo gestiona RabbitMQ, el límite de 10 lo
  gestiona el código

  ¿Esta topología tiene sentido? ¿Querés ajustar el TTL de 30s o el límite de
  10?

❯ fanout.retry es por usuario no?                                               

⏺ No, es una sola cola compartida. La granularidad por follower está en el
  contenido del mensaje, no en el nombre de la cola.

  Cada mensaje en fanout.retry representa un write fallido para un follower
  específico:

  {
    "follower_id": "uuid-de-X",
    "tweet": { "id": "...", "content": "...", ... }
  }

  Si un tweet tiene 1000 followers y falla para 50 de ellos, se publican 50
  mensajes independientes en la misma cola fanout.retry. Cada uno tiene su
  propio x-death counter, así que el límite de 10 reintentos aplica por follower
   por tweet.

  Crear una cola por follower sería impracticable — potencialmente millones de
  colas dinámicas en RabbitMQ.

  ¿Esto está claro? ¿Seguimos con la sección 2?
