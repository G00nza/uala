❯ when should you use one or the other?                                         

⏺ Good question. The deciding factor is who controls the deployment environment.

  Library-only (auto-migrate on startup) — the server runs migrations itself
  before serving traffic.
  - Good when: you own the infra, it's a simple service, downtime between deploy
   and ready is acceptable, or you want zero manual steps (common in
  katas/demos).
  - Bad when: you have multiple replicas racing to migrate on startup, you need
  DBAs to review schema changes before they run, or you need a dry-run /
  rollback step separate from the deploy.

  Separate CLI step (make migrate before go run) — migrations are an explicit,
  independent operation.
  - Good when: you have CI/CD pipelines where migrations run before the new
  binary rolls out, you want human approval before schema changes land, or you
  have multiple services sharing the DB.
  - Bad when: it's a dev-only project and the extra step just adds friction with
   no safety benefit.

  For this kata specifically: reviewers will be looking at whether you
  understand that production systems need the CLI step. But since the service is
   a single-binary with no orchestration, auto-migrate on startup is also
  defensible — and simpler to demo. The real signal reviewers want to see is
  that migrations are versioned and tracked (i.e., a schema_migrations table
  exists), not whether you used a CLI or not.

  So: which matters more to you here — showing production-grade separation of
  concerns, or keeping the demo simple to run?

❯ Separate CLI step                                                             

⏺ Three options worth considering for the CLI approach:

  Option A — golang-migrate (library + CLI)
  - Most widely used in Go. SQL files only, no Go code in migrations. Simple
  numbered filenames (000001_create_users.up.sql / .down.sql). Has a pgx/v5
  driver. CLI is a separate binary you install or invoke via go run.
  - Trade-off: verbose filenames, requires installing the CLI tool separately.

  Option B — goose (library + CLI)
  - Also very popular. Supports both SQL files and Go migrations. Simpler
  filenames (00001_create_users.sql with -- +goose Up / -- +goose Down markers
  inside). Can embed the CLI in your own cmd/migrate/main.go using its library —
   no external tool needed.
  - Trade-off: the in-file markers feel slightly non-standard to some, but the
  embedded CLI approach is clean for a kata.

  Option C — embed SQL + custom runner (no external lib)
  - Write the SQL files yourself, embed them with //go:embed, track applied
  migrations in a schema_migrations table, build your own cmd/migrate/main.go.
  Zero new dependencies.
  - Trade-off: you're reimplementing what goose/golang-migrate already do. Fine
  for showing you understand the concept, but reviewers may see it as
  reinventing the wheel.

  My recommendation: goose — you get a real, recognisable tool, you can embed
  the CLI into cmd/migrate/main.go with no external binary install, and it
  integrates cleanly with pgx/v5 via its database/sql compatibility layer. One
  go run ./cmd/migrate up and you're done.

  Does goose work for you, or do you prefer one of the others?

  Section 1 — File layout

  migrations/
    00001_create_users.sql

    00003_create_follows.sql

  Each SQL file uses goose markers:

  -- +goose Up
  CREATE TABLE users (...);

  -- +goose Down
  DROP TABLE users;

  The SQL files are embedded into the binary via //go:embed migrations/*.sql in
  the migrate command — no filesystem dependency at runtime.

  func main() {

      // reads DB URL via infra.LoadConfig()

⏺ Section 3 — Error handling & testing

  The CLI exits with a non-zero code on any error (connection failure, migration
   failure) so CI can catch it. No retries — if the DB isn't up, the operator
  fixes it and re-runs.

  assumes the DB is already migrated before it starts — if it isn't, queries
  will fail fast with clear Postgres errors, which is the correct production
