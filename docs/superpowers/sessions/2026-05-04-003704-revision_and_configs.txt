  ---
  🔴 Gap crítico real

  Celebrity/hot user problem — el fanout de 100 workers no escala a millones de 
  seguidores

  El enunciado pide explícitamente escalar a millones de usuarios. Con 100
  goroutines concurrentes, un tweet de un usuario con 10M seguidores requiere
  10M escrituras a Redis. Cada escritura incluye ZADD + HSetNX → 20M
  operaciones. Esto bloquea el consumer de RabbitMQ durante minutos.

  Lo esperado: modelo híbrido push/pull — fanout solo hacia usuarios "activos"
  (última actividad < N horas), los seguidores de celebrities reciben pull-based
   timeline al leer.

  ---
  🟠 Gaps medios

  Sin reconexión AMQP

  rabbitmq.Connect() abre una conexión una sola vez. Si RabbitMQ cae o la red se
   interrumpe post-startup, los tres goroutines consumidores mueren y nunca se
  recuperan. openChannel() en el consumer intenta una vez y retorna nil sin loop
   de reconexión.

  Publisher abre un nuevo channel por mensaje

  En publisher.go, cada llamada a publish() crea un conn.Channel(), publica, y
  cierra. Los AMQP channels están diseñados para ser long-lived. Bajo carga
  moderada esto genera overhead significativo de round-trips con el broker.

  Sin paginación en timeline

  GET /timeline devuelve hasta TIMELINE_LIMIT (500) items en una sola respuesta
  JSON. No hay cursor, page token ni limit/offset. El OpenAPI spec lo menciona
  como backlog pero no está implementado. Para lecturas optimizadas a escala,
  esto es un gap real.

  ---
  🟡 Gaps bajos

  Discrepancia documentación-código en Redis

  docs/iterations/iter-2-redis.md y docs/tradeoffs/redis-timeline-storage.md
  documentan la estrategia "JSON completo como member del sorted set". El código
   real usa sorted set (ID como member) + hash separado
  (timeline:data:{user_id}). La implementación real es la alternativa del
  tradeoff doc, no la estrategia documentada.

  Sin TTL en claves de Redis

  timeline:{user_id} y timeline:data:{user_id} nunca expiran. El allkeys-lru de
  Redis funciona como safety net pero usuarios inactivos acumulan timelines
  obsoletos indefinidamente. TTLs explícitos darían mejor control de memoria.

  Tests de integración no cubren el path async

  Los integration tests usan noopTweetPublisher y noopFollowPublisher. El flujo
  real de producción (HTTP → RabbitMQ → consumer → Redis fanout → GET timeline
  desde Redis) nunca se testea end-to-end. Solo el repository layer de Redis y
  Postgres se testa en aislamiento.

⏺ El gap 2 es reconexión AMQP cuando la conexión cae post-startup. Hay dos capas
   a resolver:

  ---
  El problema actual

  // client.go — una sola conexión, sin reconexión
  func Connect(url string) (*amqp.Connection, error) {
      conn, err := amqp.Dial(url)
      // si esta conn cae después, nadie la recupera
  }

  // consumer.go — openChannel falla silenciosamente y el goroutine muere
  func (c *Consumer) openChannel(queue string) (*amqp.Channel, <-chan 
  amqp.Delivery) {
      ch, err := c.conn.Channel()
      if err != nil {
          log.Printf(...)
          return nil, nil  // goroutine retorna → consumer muerto para siempre
      }
  }

  ---
  La solución: dos niveles

  Nivel 1 — Detectar que la conexión cayó

  amqp.Connection expone un canal de notificación:

  notifyClose := conn.NotifyClose(make(chan *amqp.Error, 1))
  <-notifyClose  // se cierra cuando la conexión cae

  Nivel 2 — Loop de reconexión con backoff

  La forma más limpia es un wrapper que encapsula la reconexión y expone siempre
   una conexión válida:

  type ResilientConn struct {
      url  string
      mu   sync.RWMutex
      conn *amqp.Connection
  }

  func (r *ResilientConn) reconnectLoop(ctx context.Context) {
      backoff := time.Second
      for {
          conn, err := amqp.Dial(r.url)
          if err != nil {
              log.Printf("amqp: reconnect failed: %v, retrying in %s", err,
  backoff)
              select {
              case <-ctx.Done():
                  return
              case <-time.After(backoff):
                  backoff = min(backoff*2, 30*time.Second)
                  continue
              }
          }
          r.mu.Lock()
          r.conn = conn
          r.mu.Unlock()
          backoff = time.Second  // reset al reconectar

          notifyClose := conn.NotifyClose(make(chan *amqp.Error, 1))
          select {
          case <-ctx.Done():
              return
          case <-notifyClose:
              log.Printf("amqp: connection lost, reconnecting...")
          }
      }
  }

  func (r *ResilientConn) Channel() (*amqp.Channel, error) {
      r.mu.RLock()
      defer r.mu.RUnlock()
      return r.conn.Channel()
  }

  Nivel 3 — Los consumers también deben reiniciarse

  El consumer no puede ser un goroutine que muere. Necesita un loop propio:

  func (c *Consumer) runWithReconnect(ctx context.Context, queue string, handler
   func(context.Context, amqp.Delivery)) {
      for {
          select {
          case <-ctx.Done():
              return
          default:
          }

          ch, msgs := c.openChannel(queue)
          if ch == nil {
              time.Sleep(2 * time.Second)
              continue
          }

          notifyClosed := ch.NotifyClose(make(chan *amqp.Error, 1))
          for {
              select {
              case <-ctx.Done():
                  ch.Close()
                  return
              case <-notifyClosed:
                  // canal cayó, reiniciar loop externo
                  goto reconnect
              case d, ok := <-msgs:
                  if !ok {
                      goto reconnect
                  }
                  handler(ctx, d)
              }
          }
      reconnect:
          ch.Close()
      }
  }

  Y los consumers en main.go quedan:

  go consumer.runWithReconnect(ctx, rabbitmq.QueueTweetCreated,
  consumer.handleTweetCreated)
  go consumer.runWithReconnect(ctx, rabbitmq.QueueFollowCreated,
  consumer.handleFollowCreated)
  go consumer.runWithReconnect(ctx, rabbitmq.QueueFanoutRetry, ...)

  ---
  Por qué en dos niveles y no solo uno

  ┌──────────────────────────────────────────┬──────────────────────────────┐
  │         Solo reconectar la conn          │   Solo reiniciar channels    │
  ├──────────────────────────────────────────┼──────────────────────────────┤
  │ La conn nueva resuelve conn.Channel()    │ Los channels mueren cuando   │
  │                                          │ la conn muere                │
  ├──────────────────────────────────────────┼──────────────────────────────┤
  │ Los channels existentes sobre la conn    │ No ayuda si la conn cayó     │
  │ vieja siguen muertos                     │                              │
  └──────────────────────────────────────────┴──────────────────────────────┘

  Necesitás ambos: la conn se recupera sola, y los consumers detectan que su
  channel cerró y piden uno nuevo a la conn ya recuperada.

  Alternativa más simple (sin wrapper)

  Si no querés el wrapper, podés pasar la url string al consumer en lugar de
  *amqp.Connection y que el consumer llame a amqp.Dial dentro de su propio loop.
   Más acoplado pero más fácil de entender a primera vista.
