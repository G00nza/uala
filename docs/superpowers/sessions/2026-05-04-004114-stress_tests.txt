⏺ Entendido, Python puro sin dependencias externas. Con la stdlib (asyncio,
  http.client, concurrent.futures) se puede hacer todo lo que necesitás.

⏺ Hay tres formas de encarar el script con stdlib pura:

  ---
  Opción A — ThreadPoolExecutor + http.client (recomendada)

  Un pool de threads donde cada thread simula un usuario virtual. El ramp-up
  agrega threads gradualmente. Simple, predecible, y en una M3 Pro podés llevar
  cómodamente 200-500 threads concurrentes antes de que el OS sea el cuello de
  botella. El output es un CSV de métricas + resumen por consola.

  Trade-off: los threads tienen overhead de memoria (~1MB cada uno), así que más
   de 1000 VUs simultáneos empieza a ser caro para el cliente.

  ---
  Opción B — asyncio + loop.run_in_executor

  Una corrutina por usuario virtual, pero las llamadas HTTP son bloqueantes así
  que igual usa un thread pool por debajo. Es más complejo sin beneficio real
  frente a la opción A para este caso.

  Trade-off: complejidad extra sin ganancia práctica cuando el I/O ya es
  bloqueante.

  ---
  Opción C — multiprocessing + http.client

  Múltiples procesos en lugar de threads, evita el GIL completamente. Útil si el
   cuello de botella fuera CPU pura, pero para I/O de red es overkill y complica
   compartir métricas entre procesos.

  Trade-off: complejidad alta, beneficio marginal para carga de red.

  ---
  Mi recomendación es la A. Es la más directa, transparente y más fácil de
  ajustar el ramp-up. ¿La encaramos así?

⏺ Diseño — Sección 1: Estructura general y fases

  El script tiene dos fases bien separadas:

  Fase 1 — Seed (setup)
  Corre antes de la carga. Crea N usuarios vía POST /users y genera una red de
  follows aleatoria (POST /follow) para que el timeline tenga contenido. Además,
   publica un lote inicial de tweets por usuario para que GET /timeline devuelva
   datos reales desde el arranque. Todo esto corre en paralelo con un
  ThreadPoolExecutor de tamaño fijo para no saturar la API durante el setup.

  Configurable: --users 100 --tweets-per-user 10 --follows-per-user 20

  Fase 2 — Load (ramp-up + sostenida)
  El ramp-up agrega workers en oleadas cada N segundos hasta alcanzar el máximo
  de VUs. Cada worker es un loop infinito que elige la siguiente operación según
   el peso 80/15/5 y la ejecuta inmediatamente. El ramp-up para cuando se llega
  al máximo de VUs o cuando el servidor empieza a responder con errores
  persistentes.

  Configurable: --max-vus 500 --ramp-step 50 --ramp-interval 10s --duration 120s

  Parámetros globales: --target http://192.168.x.x:8080 para apuntar al servidor
   remoto.

⏺ Diseño — Sección 2: Métricas y output

  Métricas recolectadas por el script:

  Cada request registra: timestamp, endpoint, latencia (ms), HTTP status code.
  Los workers escriben a una cola thread-safe (queue.Queue) y un thread colector
   centralizado drena esa cola cada segundo.

  Output en tiempo real (consola):
  Cada 5 segundos imprime una línea con el estado actual:

  [t=30s] VUs: 150 | RPS: 842 | p50: 12ms | p95: 87ms | p99: 210ms | errors:
  0.3%
    timeline: p95=45ms  tweets: p95=120ms  follow: p95=95ms

  Output final:
  Al terminar la prueba genera dos archivos en el directorio desde donde se
  corre el script:

  - results_<timestamp>.csv — todos los requests crudos (timestamp, endpoint,
  latency_ms, status)
  - summary_<timestamp>.txt — resumen por endpoint: p50/p95/p99, throughput,
  error rate, total requests

  El CSV es importable directamente en el Grafana que ya tenés si querés cruzar
  con las métricas del servidor (Prometheus).

  Criterios de corte automático: si el error rate supera el 20% durante 10
  segundos consecutivos, el script para el ramp-up y mantiene el nivel actual de
   VUs para evitar tumbar el servidor.

⏺ Muy buen caso de prueba — con TTL de 30s, los usuarios que duermen 45s van a
  tener el cache frío cuando vuelvan, así que el GET /timeline va a tener que ir
   a Postgres. Eso mide exactamente el costo del cache miss.

  Diseño actualizado — Fase 2, comportamiento de VUs:

  Al crear cada worker, se le asigna aleatoriamente un perfil:

  - 50% — Always-on: loop continuo, nunca duerme. Son los que sostienen la carga
   base.
  - 25% — Cycler: alterna entre 15s activo (loop normal) y 45s durmiendo. Con
  TTL=30s, cada vez que vuelven su cache está frío, así que su primer GET 
  /timeline siempre es un miss.
  - 25% — One-shot: corre el loop durante un período aleatorio entre 10s y 60s,
  luego termina definitivamente. El worker se descarta y no se reemplaza.

  El reporte en tiempo real va a mostrar cuántos VUs están activos en cada
  momento (los cyclers y one-shots reducen el número efectivo con el tiempo), lo
   que ayuda a interpretar las métricas:

  [t=60s] VUs: 150 (active: 112) | RPS: 634 | p95: 143ms | cache-miss estimado:
  ~25%

  El p95 más alto en los cyclers vs always-on va a ser visible en el CSV si
  filtrás por VU profile.
