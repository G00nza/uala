⏺ Tengo todo lo que necesito. Tres enfoques para resolver el cursor en Redis (el
   nodo más complejo):

  ---
  Opción A — ZREVRANK + índice (recomendada)

  Para after=<id>: ZREVRANK(key, id) → rank → ZREVRANGE(key, rank+1, rank+20).
  Para before=<id>: rank → ZREVRANGE(key, rank-20, rank-1).
  Si ZREVRANK devuelve nil (tweet no está en Redis) → fallback directo a
  Postgres.
  Pros: simple, O(log N), sin ambigüedad. Cons: si el tweet del cursor fue
  eliminado de Redis por TTL/trim, va a Postgres; eso está bien porque tú
  dijiste que es aceptable.

  ---
  Opción B — ZSCORE + rango por score

  ZSCORE(key, id) → unix timestamp → ZREVRANGEBYSCORE key "(score" -inf LIMIT 0 
  20.
  Pros: idiomático para sorted sets por score. Cons: tweets con el mismo segundo
   exacto de created_at pueden quedar mal ordenados (empate de score sin
  desempate secundario); requiere manejo extra.

  ---
  Opción C — Redis solo para página 1, Postgres para todo lo paginado

  Sin cursor → Redis. Con cursor (after/before) → siempre Postgres.
  Pros: máxima simplicidad, cero lógica especial en Redis. Cons: pierde el
  beneficio del cache para páginas 2-25 (las primeras 500 entradas), lo cual es
  la mayor parte del uso real.

  ---
  Mi recomendación es A. Es directa, usa ZREVRANK que ya está disponible, y el
  fallback a Postgres cuando el cursor no está en Redis es exactamente el
  comportamiento que pediste. ¿Avanzamos con esa?

⏺ Diseño — Sección 1: API y contratos

  Endpoint: GET /timeline?user_id=<uuid>[&after=<tweet_id>][&before=<tweet_id>]
  - Sin cursor → primera página (20 tweets más recientes)
  - after=<id> → página siguiente (tweets más viejos que id)
  - before=<id> → página anterior (tweets más nuevos que id)
  - after y before son mutuamente excluyentes; si se envían ambos → 400

  Respuesta:
  {
    "tweets": [...],
    "next_cursor": "<tweet_id | null>",
    "prev_cursor": "<tweet_id | null>"
  }
  - next_cursor: ID del último tweet devuelto (para pedir página siguiente).
  null si no hay más.
  - prev_cursor: ID del primer tweet devuelto (para pedir página anterior). null

⏺ Diseño — Sección 2: Lógica Redis y fallback a Postgres

  Redis (ZREVRANK approach):

  Sin cursor (primera página):
  - ZREVRANGE(key, 0, 19) → 20 tweets más recientes

  after=<id> (siguiente página, tweets más viejos):
  - ZREVRANK(key, id) → rank
  - Si nil → fallback a Postgres
  - ZREVRANGE(key, rank+1, rank+20)

  before=<id> (página anterior, tweets más nuevos):
  - ZREVRANK(key, id) → rank
  - Si nil → fallback a Postgres
  - ZREVRANGE(key, max(0, rank-20), rank-1) → luego revertir para mantener orden
   DESC

  Si la key no existe en Redis → cache miss normal → cargar desde Postgres,
  escribir en Redis, paginar desde Redis.

  Postgres fallback (cuando cursor no está en Redis):
  -- after=<id>
  WHERE f.follower_id = $1
    AND t.created_at < (SELECT created_at FROM tweets WHERE id = $cursor)
  ORDER BY t.created_at DESC LIMIT 20

  -- before=<id>
  WHERE f.follower_id = $1
    AND t.created_at > (SELECT created_at FROM tweets WHERE id = $cursor)
  ORDER BY t.created_at ASC LIMIT 20
  -- luego revertir resultado a DESC
