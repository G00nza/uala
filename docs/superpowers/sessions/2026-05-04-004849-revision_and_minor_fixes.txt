  ---
  Gaps encontrados

  Criterios de evaluación

  1. Documentación high-level sin punto de entrada único
  La consigna pide "documentación high level de la arquitectura y los
  componentes usados." Hay architecture.svg, docs por iteración en
  docs/iterations/, tradeoffs en docs/tradeoffs/, y el README tiene info de uso
  — pero no existe un documento único que narrativamente explique qué hace cada
  componente y por qué fue elegido. Un evaluador tiene que reconstruir el cuadro
   completo navegando múltiples archivos.

  2. OpenAPI desactualizado
  docs/api/openapi.yaml tiene este comentario en el description:
  ## Backlog
  - Paginación en `GET /timeline`
  Pero la paginación cursor-based ya está implementada (params after/before,
  respuesta con next_cursor/prev_cursor). El spec no documenta ninguno de esos
  campos. Un evaluador que lea el spec va a pensar que falta paginación.

  ---
  Setup / DevEx

  3. Race condition en make up
  up:
      docker-compose up -d      # containers arrancando en background
      go run ./cmd/api/...      # app arranca inmediatamente
  Sin esperar healthchecks de Postgres/Redis/RabbitMQ, el app falla si la infra
  no está lista. Un make up limpio desde cero probablemente crashee en el primer
   intento.

  4. AMQP_URL ausente en .env.example
  El README documenta AMQP_URL como variable requerida y el app falla sin
  RabbitMQ, pero .env.example no la incluye. El .env real sí la tiene, pero está
   gitignoreado. Un dev que clone el repo y haga cp .env.example .env quedará
  sin esa variable.

  5. Sin target make test-integration
  El Makefile solo expone make test (unit tests). Los integration tests
  requieren INTEGRATION=1 go test ./... — esto está documentado en el README
  pero no como target de make, que es donde la mayoría buscaría primero.

  ---
  business.txt

  6. Ausente: assumption de celebrity fanout / usuarios activos
  El sistema tiene una decisión de negocio significativa: solo los followers 
  activos en el último ACTIVITY_TTL (default 24h) reciben el tweet en tiempo 
  real. Un follower inactivo no verá el tweet de quienes sigue hasta que entre y
   refreshee su timeline desde Postgres. Esto no está documentado en
  business.txt.

  ---
  Código

  7. Logging inconsistente: log.Printf vs slog
  Todo el codebase usa slog con logging estructurado, pero
  internal/messaging/rabbitmq/consumer.go (17 calls) y
  internal/usecase/timeline.go usan log.Printf. Los errores del consumer — que
  incluyen failures de fanout, reintentos, dead letters — salen sin estructura
  JSON.

  ---
  Testing

  8. El path async (fanout) no tiene ningún test de integración
  No existe ningún test que verifique que un tweet publicado eventualmente
  aparece en el timeline de los followers. El CLAUDE.md lo justifica ("el
  contrato de serialización lo garantizan los tipos compartidos"), pero el
  comportamiento observable del feature principal — timeline mostrando tweets de
   seguidos — no está cubierto en ningún test de integración de punta a punta.

       84 +Durante la implementación inicial el timeline se almacenaba co
          +mo JSON completo en el member del Sorted Set. Al introducir el
          + fanout selectivo, cada tweet se escribe múltiples veces (una 
          +por seguidor activo). Con JSON como member, cada escritura dup
          +lica el payload completo en Redis.                            
       85 +                                                              
       86  ### Decisión
       87  
       70 -Dos niveles de test:                                          
       88 +Separar en dos estructuras:                                   
       89  
       90 +```                                                           
       91 +timeline:{user_id}       →  Sorted Set  (score: unix timestamp
          +, member: tweet_id)                                           
       92 +timeline:data:{user_id}  →  Hash        (field: tweet_id, valu
          +e: JSON del tweet)                                            
       93 +```                                                           
       94 +                                                              
       95 +La lectura combina `ZREVRANGE` + `HMGET`. La escritura usa `HS
          +etNX` (idempotente): si el tweet ya existe en el hash, no se r
          +eescribe el payload.                                          
       96 +                                                              
       97 +### Comportamiento de TTL                                     
       98 +                                                              
       99 +- **En write (fanout):** `ExpireNX` — setea TTL solo en keys n
          +uevas, no sobreescribe el TTL de keys existentes.             
      100 +- **En read:** `Expire` — renueva el TTL al valor completo de 
          +`ACTIVITY_TTL`, extendiendo la ventana de actividad.          
      101 +- Las keys expiran naturalmente cuando el usuario pasa a inact
          +ivo, sin eviction explícita.                                  
      102 +                                                              
      103 +### Consecuencias                                             
      104 +                                                              
      105 +- Un read requiere dos round-trips a Redis en lugar de uno. En
          + la práctica, Redis pipeline los hace casi en paralelo.       
      106 +- La separación habilita `HSetNX` idempotente en el fanout: el
          + mismo tweet puede llegar dos veces sin duplicar datos.
