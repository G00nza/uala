⏺ La situación actual: cada struct ya tiene un solo método de negocio
  (CreateTweet, Follow, GetTimeline, Create), así que ya estás a mitad de
  camino. La pregunta real es si vale la pena el paso final: renombrar a
  CreateTweetUseCase{}.Execute().

  Mi opinión honesta: el patrón es válido pero tiene un trade-off claro en Go.

  A favor:
  - API uniforme: todo use case tiene .Execute(ctx, input), los handlers se
  vuelven predecibles
  - El verb en el nombre del struct deja claro la intención sin ambigüedad:
  CreateTweetUseCase vs TweetUseCase
  - Es lo que recomienda el skill golang:usecase-layer de este proyecto

  En contra:
  - uc.Execute(ctx, ...) en el call site dice menos que uc.CreateTweet(ctx, ...)
   — perdés contexto sin ganar nada funcional
  - En Go idiomático el nombre del método es semántico; Execute es más Java/C#
  (Command Pattern)
  - Refactor no trivial: hay que tocar handlers, mocks en tests, y los handlers
  tienen mini-interfaces privadas para tests

  ¿Es anti-patrón Go? No exactamente. Es una adaptación del Command Pattern que
  funciona bien, pero no es el estilo más "Go-nativo". La guía oficial de Go
  prefiere métodos con nombres descriptivos.

  Mi recomendación para este kata: si el objetivo es aprender arquitectura
  limpia, adoptá el patrón del skill (CreateTweetUseCase{}.Execute()) — es una
  decisión de diseño coherente y defendible. Si el objetivo fuera producción, me
   quedaría con los nombres descriptivos actuales y solo separaría en
  subpaquetes si los structs crecen.

  El costo del refactor en este repo es bajo (4 use cases, structs pequeños). Si
   querés hacerlo, puedo guiarte.
