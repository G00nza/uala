❯ si renombro la carpeta internal a src rompo algun standard de go?             

⏺ Sí, romperías algo importante. internal en Go no es solo convención — es una 
  regla del compilador.

  El toolchain de Go impone que solo el código que vive en el árbol padre de
  internal/ puede importar paquetes de adentro. En tu caso, con
  uala/internal/..., cualquier módulo externo que intente importar esos paquetes
   recibe un error de compilación. Es el mecanismo de encapsulación a nivel de
  módulo que Go provee de forma nativa.

  Si lo renombrás a src/:
  - Perdés esa protección — cualquier módulo externo podría importar tus
  paquetes internos
  - src/ está desaconsejado en Go moderno (es un rezago de la era GOPATH, antes
  de modules)
  - El layout estándar de proyectos Go usa internal/ para código privado del
  módulo

❯ cuan costoso es unificar TweetItem y Tweet?                                   

  Searched for 3 patterns, read 2 files (ctrl+o to expand)

⏺ La diferencia clave entre los dos:

  ┌──────────┬─────────────────────────────────┬────────────────────────────┐
  │          │              Tweet              │         TweetItem          │
  ├──────────┼─────────────────────────────────┼────────────────────────────┤
  │ Campos   │ ID, UserID, Content, CreatedAt  │ + Username                 │
  ├──────────┼─────────────────────────────────┼────────────────────────────┤
  │ JSON     │ no                              │ sí                         │
  │ tags     │                                 │                            │
  ├──────────┼─────────────────────────────────┼────────────────────────────┤
  │ Uso      │ escritura                       │ lectura (timeline, fanout, │
  │          │ (TweetRepository.Create)        │  redis)                    │
  └──────────┴─────────────────────────────────┴────────────────────────────┘

  Tweet es el modelo de escritura — no necesita Username porque está en la tabla
   users. TweetItem es el modelo de lectura desnormalizado, con Username para
  evitar joins en cada lectura de timeline.

  Costo de unificar: moderado pero mecánico.

  - Tweet ganaría Username y json tags → el postgres repo que hace Create ignora
   ese campo (o lo recibe vacío), lo cual es un poco raro
  - Habría que actualizar CreateTweetUseCase para poblar Username antes de
  persistir (hoy no lo hace)
  - ~10 archivos tocados, la mayoría cambios de tipo

  La tensión real: si unificas, el modelo de escritura carga un campo que la
  capa de persistencia no usa. Si no unificas, seguís con dos structs casi
  idénticos. La pregunta es si Username en el write path tiene sentido
  semánticamente — probablemente no, porque el username lo resuelve la DB via
  JOIN.

  Mi recomendación: si querés limpieza, el punto de dolor real es que TweetItem
  está definido en follow.go, que es un lugar raro. Moverlo a tweet.go como tipo
   propio ya da mucho orden sin el costo de mezclar modelos de
  lectura/escritura.
